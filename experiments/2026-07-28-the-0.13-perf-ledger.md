# The 0.13 perf ledger (2026-07-28)

The hash-neutral performance pass, measured — what shipped, and what
was refused with numbers so nobody re-proposes it from static
reading. Provenance: branch `0.13.0`, release build, macOS `sample`
at 1 ms over the honest bench (`driver bench --scenario
scenarios/compass-grand.json --ticks 100000`, stops at the decision,
tick 16029), on the binary that already carries the tick's spatial
index. Shares are of total process samples (~2,270 per 3 s window).

## The spatial index aftermath

With collision and acquisition off the top of the profile, the tick
reads:

| phase (call-graph subtree) | samples | share |
|---|---|---|
| `brain::run` (acquisition, economy, locomotion, siting) | 880 | 39% |
| `resolve_collisions` (pair loop + `row_span` + rebuilds) | 546 | 24% |
| `vision::refresh` | 341 | 15.0% |
| bot minds outside the tick (neural `act`) | ~430 | 19% |
| `movement::run` | 58 | 2.6% |

Top-of-stack, cutting across those subtrees: `acquire_target` +
its `row_span` calls ~310, `State::passable` + `passable_for` 187
(8.2%), the `UnitIndex::rebuild` sorts ~100 (4.4%). Vision's share
rose from 10.2% exactly as predicted — the denominator halved, the
absolute cost did not move.

## Shipped: the vision memory walk, fused

The reconciliation loop walked the whole grid twice per team per
tick — once copying `tile.scrap` into `remembered_scrap`, once
re-fetching the same rows to copy `tile.wreck`. Fused to one walk:
rows fetched once, both memories written under one `seen` test.
Identical writes to identical cells, so hash-neutral by
construction; the fixture suite passes unblessed and both benches
report identical hashes and the identical decision tick.

Measured (release, 3 runs each):

- compass-grand, stops at decision: 4432 / 4433 / 4425 ->
  **4536 / 4534 / 4529 ticks/s** (+2.3%)
- 500-unit mass battle, 2000 ticks: 11591 / 11957 / 12081 ->
  **12601 / 12702 / 12532 ticks/s** (+5%)

The post-change profile confirms the mechanism: the reconciliation
walk fell 81 -> 31 samples; everything else in the phase held still.

## Refused: the span-scoped vision clear

The proposal: have `stamp_disc`/`stamp_rect` record each written
span, clear only last tick's spans instead of `fill(false)`, and
reconcile only this tick's spans instead of the whole grid. The
fresh profile refuses it three ways:

1. The clear it removes is one contiguous W*H memset per team per
   tick — 6.7 KB on compass-grand, noise. The memset time that DOES
   show in the phase (~90 samples) sits under the per-row span
   fills of the disc/rect stamps, which the change does not remove
   and actively taxes with a push per span in the hottest loop.
2. The scan it scopes visits the SUM of disc areas, not the union.
   At measured deep-game army sizes (183-386 units alive) the raw
   span list is ~45-70k cell-visits per team-tick against the full
   walk's 6,784. Making spans beat the walk needs a per-row merge,
   and the merge's sort costs the order of the walk it saves.
3. What remains addressable after the fusion is the 31-sample walk
   itself — 1.4% of tick time — bought with a persistent scratch
   threaded through the tick (it cannot live on `Vision`: `State`
   serializes for the hash and derives `PartialEq`) and a
   stale-visible failure mode that is a fog leak, not a perf
   regression.

Trigger to revisit: map classes well beyond 124x78 or team counts
beyond 2. The phase scales with W*H x teams while the span count
scales with army size, so a much larger grid moves the arithmetic —
re-profile there before building anything.

## Refused: the tile-to-building index

The proposal (Codex, from static reading): `building_at` is a linear
scan and `passable` calls it from A* node expansion, collision
candidate validation, waypoint revalidation, goal snapping, and half
a dozen siting checks — index buildings by tile.

The measurement refuses the premise: the scans are over the SMALL
collection. Shipped matches peak in the teens of buildings
(compass-grand at ticks 4k/8k/12k/16k: 15/15/16/8 standing against
183/386/294/124 units), so `building_at` is ~15 four-comparison
rectangle tests. Profiled share: 2.9% top-of-stack pre-spatial-index,
187 samples = 8.2% on the post-index profile — the share doubled
because the denominator halved, the absolute cost is unchanged. A
rising share on a falling denominator is not a regression.

Trigger: the index earns its keep when shipped matches routinely
carry more than roughly **60 standing buildings** — a deeper tech
tree, walls, heavy static defense. At that point the call site that
hurts is A* node expansion, not the movement revalidation. Hit these
numbers with a fresh profile before building it.

If it is ever built, the shape that pays: a `Grid` of building ids
kept beside the tick as non-state cache — never a plain `State` or
`Map` field (both serialize into the hash, and `#[serde(skip)]`
still poisons the derived `PartialEq`), so it means a hand-written
`PartialEq` plus invalidation at exactly four mutation sites
(placement, completion, destruction, salvage) with a debug assertion
against a linear rebuild. Hash-neutral by construction — footprints
never overlap, so an index returns `building_at`'s exact answer. The
tempting cheap alternative — sort `buildings` by anchor row and
binary-search the y-band — is NOT cheap: several `buildings.iter()`
consumers are order-sensitive (the direct-hit rule documents "first
hostile footprint in id order takes the hit"), so re-sorting is
hash-moving.
